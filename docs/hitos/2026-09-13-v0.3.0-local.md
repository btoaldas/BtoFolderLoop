# v0.3.0 local development milestone

Scope: improve operation history/retention, add signed one-click application updates and multiple-folder/shortcut inputs while keeping the existing installed cleanup undisturbed. The observed cleanup subsequently completed. Publication and installation are not included.

## Changes

- Live counters are persisted in the same SQLite statement/transaction as each event. History shows the worked-on root, operation mode, result counters and local activity time. Per-run events are paginated in batches of 200; history lists show the latest 200 operations or roots.
- Typed diagnostic records carry UTC timestamps, level, event code, optional run identifier and count. No user paths or arbitrary error text is accepted. Progress diagnostics are sampled every ten seconds; recovery journals retain each prepared/result pair.
- Diagnostic defaults: 30 days, total 10 MiB, segments up to 2 MiB with daily rotation. Completed history defaults: 180 days. Both day limits and the diagnostic byte budget are editable.
- Retention only expires consistent completed history. Running, cancelled, stopped, errored and unresolved operations remain. It never acts on source folders or Trash destinations. Settings explain that expired completed history loses its recovery paths.
- Additive schema 2 reconstructs legacy counters and saves a private online SQLite backup before upgrading schema 1. The backup is retained separately. SQLite reuses freed pages rather than running a disruptive automatic VACUUM.

## Remaining distribution checks

Do not replace or restart an application during cleanup. A future authorized release must repeat final package/source checks, interactive isolated UI smoke tests and compatible installation/migration validation after the active operation is over. The application is still locally ad-hoc signed, not Apple-notarized; broader OS/provider coverage remains pending. The latest public release remains v0.2.0.

Rollback of uninstalled code uses the preceding commit. A schema-1 backup is a historical snapshot, not a safe automatic rollback after later schema-2 operations. Preserve newer journals and review any restoration separately. No private database or raw operational history belongs in a knowledge-vault snapshot.
